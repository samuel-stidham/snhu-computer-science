**Course Description:**
Students will learn to create structured database environments that incorporate basic processing functionality and allow for data management, data manipulation, and data analysis. Students will also construct and analyze queries to address data requirements.

---

## Key Topics & Concepts

This course builds a relational database from the query language up, one zyBook chapter per module across Modules One through Five. Each of those modules carries a quiz, and most pair a Codio lab with an activity or major activity. Modules Six and Seven hold the two projects, and discussions bracket the term in Modules One, Two, and Eight. Topic summaries will be added as the course progresses.

* **Query Language Basics:** Module One, zyBook Chapter 1, with the Practicing Query Language lab in Codio.
* **Updating Tables:** Module Two, Chapter 2, with the Updating Tables and SQL Identification activity and the Updating Tables lab.
* **Table Joins & Database Creation:** Module Three, Chapter 3, with the Table Joins lab and the Create a Database major activity.
* **Cardinality & Targeted Data:** Module Four, Chapter 4, with the Cardinality and Targeted Data lab and the Load and Query the Data major activity.
* **Query Analysis:** Module Five, Chapter 5, with the Analysis and Summary activity and the Analyzing Queries major activity.
* **Foundational Competencies:**
  * **DAD-10286:** Create a structured database through the use of relational concepts.
  * **DAD-10287:** Implement basic processing functionalities to create new structured database environments.
  * **DAD-20288:** Analyze the results of queries constructed to address data requirements.

## Discussion Work & Academic Themes

The course runs three discussions: Database Basics in Module One, Databases and Businesses in Module Two, and Database Professional Roles in Module Eight. Each will be summarized below as the course progresses.

1. **Database Basics**
    * **Focus:** Introduced professional background and the goal for the course. Fourteen years of backend engineering have included a lot of repairing databases modeled badly from day one. The aim here is the vocabulary to argue against that damage in a design review, before it ships.
    * **Analysis:** Described production work in PostgreSQL, MySQL, SQLite, and MongoDB, most of it tuning: reading execution plans, adjusting indexes, and reshaping tables so common queries stop scanning everything. Recounted repairing a double-encoded table by casting the latin1 column to varbinary before converting it to utf8mb4. Also described major version upgrades on production databases with under a minute of downtime. Traced the classroom side back to Oracle 10g DBA coursework. Credited stored procedures with constraining operations inside the database, and prepared statements with keeping user input out of query text. On diagramming, argued that a diagram makes a claim about the business. Drawing one needs five things: the tracked entities, the facts recorded about each, the identifying keys, relationship cardinality and participation, and the cross-table constraints. Most of that input is business rules, expected volume, and record lifecycle rather than anything technical. Placed the approach in Chen's (1976) entity-relationship model, built on Codd's (1970) relational model.
    * **Takeaway:** Asked peers who had inherited a database they did not design how they mapped it. Closed with an aside on a personal command-line secrets manager built on SQLite (Stidham, 2026). Three strict-mode tables hold the metadata and version history. The tool seals each value in an age envelope bound to its own row before it touches disk (Valsorda & Cartwright-Cox, 2025). Building it taught more about how a SQLite write fails and how to recover than expected.

2. **Databases and Businesses**
    * **Focus:** Argued that a database turns a pile of transactions into something a business can reason about, then surveyed who uses one.
    * **Analysis:** Led with aggregation for statistical analysis: seasonal sales history proves which items sell when, and that evidence decides where the next marketing budget goes. Pointed to accounting as a second use, since every ledger entry, invoice, and payment lands in a table. A period's profit or loss and the other performance metrics come straight out of queries against those tables (Coronel & Morris, 2019). Added demographic data as a third, with Netflix treating its recommendation system as central to keeping subscribers (Gomez-Uribe & Hunt, 2015).
    * **Takeaway:** Named eCommerce, sports video and analytics, banks, and insurers as database users. Every past employer used relational databases and analysis to measure its place in the market. Stopped short of saying every business, since some still run on Excel. A VBA power user can do part of what SQL does. Most users are not, so in practice a spreadsheet stands in for a database.
